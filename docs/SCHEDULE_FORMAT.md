# Сменяемое расписание — формат и импорт

**Цель:** изменение времени намаза, новой годовой таблицы и настроек мечети **без пересборки APK**. В первой версии — без сервера и обязательного интернета.

## Хранение

- В APK можно положить стартовый подтверждённый годовой файл (при наличии подтверждения). Дополнительно хранить импортированную текущую версию в приватном хранилище приложения.
- Простой **JSON-файл** по году и мечети; SQLite/Room не нужен только ради 365 записей в одном файле. Если понадобится поиск, множество городов и история изменений, можно перейти на Room позже.
- Ключ каждой записи — **полная дата** `YYYY-MM-DD` и явный часовой пояс `Europe/Moscow`. Нельзя использовать один и тот же `DD.MM` из года в год.
- Файл расписания и настройки **икамата** логически раздельны. Икамат в MVP не вычислять из HTML-формулы +5/+10/+15 минут без подтверждения.

## Пример структуры

Файл `data/schedule_example_2026.json` — **только демонстрация формата и парсера**, неполный и недопустимый для реального табло.

```json
{
  "schemaVersion": 1,
  "locationId": "kazan-nur-islam",
  "locationName": "Нур Ислам, Казань",
  "timezone": "Europe/Moscow",
  "year": 2026,
  "source": "DEMO / NOT APPROVED",
  "revision": "example-1",
  "approved": false,
  "days": [
    {
      "date": "2026-10-23",
      "suhurEnd": "05:00",
      "fajrInMosque": "05:30",
      "sunrise": "07:00",
      "zawal": "11:30",
      "dhuhr": "12:00",
      "asr": "15:10",
      "maghrib": "17:20",
      "isha": "18:50"
    }
  ]
}
```

**Значение полей:** `fajrInMosque` — исходная формулировка колонки «Мәчеттә укыла», **не считать автоматически ни началом Фаджра, ни икаматом**. Пока смысл не подтверждён, эти значения допускаются в таблицу только как исходное поле, но не используются для расчёта намаза/икамата по неподтверждённой семантике. Зухр должен читаться из файла, а не быть постоянной `12:00`.

## Валидация перед применением

1. Проверка schemaVersion, timezone, года, полного набора дат 365/366, отсутствия дублей и пустых времён, реального формата HH:mm в диапазоне 00:00..23:59.
2. Полная проверка в памяти, **никакой частичной замены** текущего расписания.
3. Сохранение через временный файл + атомарное переключение с резервной предыдущей версией (стратегия по возможности файловой системы Android); после сбоя должна остаться целая предыдущая версия.
4. Показать администратору источник, год, число дней, revision; применить только по подтверждению.
5. Набор без `approved=true` считать демонстрационным / неподтверждённым; не включать для эксплуатации в мечети без явного решения ответственного.
6. Если на дату нет валидного расписания — вывести предупреждение, не использовать прошлогоднее.
7. Если в расписании есть аномальные переходы (как летние времена Татарстана), не «исправлять» данные без подтверждения владельца источника.

## Обновление без интернета

Предпочтительный MVP: пункт админ-меню **«Импорт расписания»**, выбор файла через Android Storage Access Framework (`ACTION_OPEN_DOCUMENT`), проверка, подтверждение и атомарное применение.

**Важная оговорка:** не на каждой TV-прошивке есть удобный файловый менеджер/доступный DocumentsProvider. При тестировании устройства проверить системный picker и USB. Если отсутствует, реализовать простой задокументированный резервный способ импорта через ADB / локальную сеть в следующем этапе, не выдавать непроверенный SAF за гарантированно работающий на всех ТВ.

В перспективе, если много мечетей, можно добавить загрузку подписанного/проверяемого файла по HTTPS с проверкой и ручным подтверждением. Сервер **не нужен** для MVP.

Пример файла лежит в `data/schedule_example_2026.json`. В релизе использовать только реально согласованный источник 2026, 2027 и последующих лет.

**Открыто:** кто конкретно утверждает расписание, источник `18:45 / 18:50` для Иша и правила икамата. См. [DATA_NOTES.md](DATA_NOTES.md).

## Реализация программного MVP

Импорт реализован в Release. Приложение принимает UTF-8 JSON до **1 МиБ**, год **2000–2200**, schemaVersion=1, строго Europe/Moscow. Даты — YYYY-MM-DD, времена — ровно HH:mm; проверяются все поля и полный набор дат. Дубли JSON-ключей, неизвестные поля, null, строки вместо boolean/чисел, некорректный UTF-8 и лишние данные после JSON отклоняются. Сезонные значения и порядок времён внутри суток не «исправляются».

### Необязательный смысл Фаджра

Допускается дополнительное поле верхнего уровня:

```json
"fajrMeaning": "UNCONFIRMED"
```

Отсутствие поля равно `UNCONFIRMED`. В этом случае источник `fajrInMosque` показывается в таблице, но утром до восхода и перед следующим неподтверждённым Фаджром вместо ошибочного countdown до Зухра выводится статус неопределённости.

**Только после подтверждения мечетью**, что колонка задаёт начало Фаджра, в утверждённом файле можно указать:

```json
"fajrMeaning": "PRAYER_START"
```

Тогда Фаджр участвует в следующем событии наравне с четырьмя остальными молитвами. Флаг не вычисляет икамат, не добавляет минуты и не разрешает произвольно выбирать Иша. Если данные задают другое понятие (например, только время коллективного чтения), используйте UNCONFIRMED до согласования отдельного правила. Новые значения enum не угадываются.

### Применение и хранение

Валидный файл с `approved=false` можно просмотреть, но применить нельзя. `approved=true` не является цифровой подписью источника: администратор отдельно подтверждает его утверждение мечетью и применение. Исходный документ, согласование Иша и смысл Фаджра остаются ответственностью владельца данных.

Два последних импорта сохраняются одним приватным атомарным envelope с контрольной суммой каждого JSON. После подтверждения запись синхронизируется и проверяется; только затем публикуется новое состояние. Прежний файл доступен для подтверждаемого отката. Повреждённая текущая версия при наличии проверенного резерва восстанавливается с уведомлением, не скрытым от администратора.

Импорт нового года можно выполнить до полуночи: предыдущий меньший год продолжает обслуживать **свои** полные даты; затем экран переходит на новый год. Это не перенос DD.MM между годами. Хранятся две версии, а не неограниченный архив. Откат к более раннему году не разрешает использовать отвергнутый будущий файл из резерва автоматически.

SAF, резервный способ через `incoming-schedule.json` и инструкции восстановления описаны в [TV_OPERATIONS.md](TV_OPERATIONS.md). API-контракт расписания наблюдаем через StateFlow, поэтому применение/откат меняют экран немедленно.
