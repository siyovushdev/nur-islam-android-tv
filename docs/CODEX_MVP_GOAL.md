# Конечная цель для Codex — готовый offline-first APK табло намазов

**Статус:** основное задание после слияния [PR #8](https://github.com/siyovushdev/nur-islam-android-tv/pull/8). Ветку создавать от актуального `main`.  
**Owner:** пользователь; автономная разработка разрешена, **merge / production deployment не разрешены** без отдельного подтверждения.

## Что считать выполненным результатом

Не отдельный каркас или прототип, а **реально собираемое, проверенное, удобное в эксплуатации НАТИВНОЕ Android TV приложение** для настенного экрана мечети «Нур Ислам» (Казань):

- Работает без интернета; **правильное расписание обновляется импортом файла без пересборки APK**.
- Есть **две переключаемые нативные темы**: Elegant — уже реализованная в PR #8, Classic — минималистичная по исходному HTML.
- Настройки доступны с **обычного ТВ-пульта в release**, позволяют сменить тему, ориентацию, масштаб/язык/подписи, импортировать и откатить расписание.
- Работают вертикальные ТВ при логическом системном разрешении landscape 1920×1080 (±90°), настоящий portrait, обычный горизонтальный экран, 720p/1080p/4K.
- Часы, дата, 8 строк (пять намазов + три справочных события), текущая/следующая молитва и обратный отсчёт не расходятся после времени/даты/сна/смены данных.
- Никаких неподтверждённых религиозных времен, икамата, Рамадана или хиджры в production.
- Подготовлен **безопасный путь автозапуска** как основного экрана HOME (где позволяет ОС) и восстановления после reboot; ограничения конкретной прошивки не скрывать.
- Исходники, unit/UI-тесты, CI, понятные инструкции, скриншоты и **Draft PR**. Release-кандидат по софту, но не заявлять production-ready без проверок на физическом ТВ и подтверждения годового расписания.

**Никакого HTML, WebView или JavaScript в APK. Только Kotlin / Compose / Android SDK.** Stitch отменён. Один app-модуль, без сервера, Room, сложной DI/фоновой платформы, если нет реальной необходимости.

## Делай работу до результата (без остановки после минимального изменения)

### Часть A: надежные сменяемые данные

Реализуй поверх текущего `ScheduleRepository` импорт валидируемого JSON, описанного в `SCHEDULE_FORMAT.md`: `YYYY-MM-DD`, конкретный год, Europe/Moscow, полный набор 365/366 дней, источник/ревизия, восемь времен в корректном формате. Встроенный demo JSON — только фикстура; **не зашивай его времена в Release**.

- Выбор файла с пульта через SAF там, где это поддерживается; диагностика/разумный fallback для ТВ без DocumentsProvider; без сервера.
- Проверка **до применения**, предпросмотр года/источника/сравнения значений, подтверждение человеком, безопасное применение и возможность восстановить предыдущий файл при сбое/откате.
- **Обновление UI сразу после импорта без закрытия APK.** Не зафиксировать в `remember(date)` репозиторий так, чтобы после замены показывались старые значения.
- Проверки повреждённого/неполного/дублирующего файла, некорректных часов, 29 февраля, отсутствующего года, рестарта, offline, имитации сбоя записи.
- Не «исправляй» сезонные времена Татарстана самовольной астрономической формулой, не подменяй официальное расписание данными из HTML.
- Есть известное несогласованное расхождение Иша 18:45/18:50 на 142 датах, а `fajrInMosque` не имеет утвержденной семантики. **Не изобретай ответ.** Должно быть возможно загрузить подтверждённый файл позже. Нельзя выдавать Зухр за «следующий намаз» утром только потому, что из расчёта исключён неопределённый Фаджр; показывай корректный статус неопределённости или подтверждённое Фаджр при утверждении правила.

### Часть B: темы и экран

Сохрани существующую **Elegant** без визуального регресса и создай **Classic** по `design/THEMES_AND_SETTINGS.md` / `design/CLASSIC_REFERENCE.svg`.

- В каждой теме нативные динамические Compose текст/времена/таймеры, а не готовая картинка.
- Тема влияет только на вид; расчет/импорт данных едины.
- Смена темы мгновенная, без потери состояния; выбранная тема переживает перезапуск.
- Расчет геометрии и вся навигация (включая настройки) корректны в AUTO / PORTRAIT_NATIVE / PORTRAIT_ROTATE_CW / PORTRAIT_ROTATE_CCW / LANDSCAPE.
- Ни одна из 8 строк не пропадает на обычном 720p/1080p/4K, не накладываются надписи при fontScale 1.3. Главное — читабельность с расстояния.

### Часть C: полноценные настройки в Release

Не оставляй меню выбора темы/поворота только в Debug. Сделай рабочие администраторские настройки для пульта D-pad с доступом на пульте **без кнопки MENU** и без тачскрина. Механизм входа не должен мешать обычной трансляции.

Минимальный состав:
- тема Elegant / Classic;
- режим AUTO / portrait native / поворот ±90° / landscape; предпросмотр и **автоматический откат**, если пользователь не подтверждает опасную смену ориентации;
- масштаб текста, двуязычное отображение (татарский/русский), имя/место мечети как подписи;
- импорт / предпросмотр / информация о подтверждении / откат расписания;
- диагностика: год/источник/ревизия, текущие время/часовой пояс, версия APK, режим экрана и тема;
- стабильное локальное сохранение настроек и разумные значения по умолчанию.
- необязательные подтвержденные настройки икамата как отдельные данные. **Никаких +5/+10/+15 по умолчанию из HTML**; если полноценные правила намаза не утверждены, не показывать готовым то, что неверифицируемо.

Не ставь слабый универсальный захардкоженный PIN; не блокируй администратора от единственного входа на ТВ.

### Часть D: автозапуск/устойчивость в границах Android

Изучи имеющуюся `MainActivity` и документацию Android dedicated devices. Реализуй безопасную штатную возможность выбора приложения как `HOME`/основного экрана (если допустимо на выбранном устройстве), keep screen on пока экран активен, обработку восстановления после процесса, перезагрузки, screen resume и смены системного времени. Документируй включение режима, отключение и возврат к штатному лаунчеру.

- Не обещай без проверки, что любой Android TV гарантированно умеет kiosk, Device Owner, управление питанием панели, HDMI-CEC или фоновой запуск Activity.
- **Не делать** бесконечные сервисы и попытки обходить background-activity restrictions.
- Без целевого ТВ считать автозапуск **неподтверждённым на железе**. Не объявлять его «готово 100%».

### Часть E: независимая проверка и передача результата

Продолжай до выполнения критериев, а не останавливайся после реализации одного экрана. Сам находи/исправляй свои баги, прогоняй `assembleDebug`, `assembleRelease`, тесты, lint, CI; не маскируй предупреждения. Добавь тесты на реальное обновление UI при импорте, замену и откат, состояние после reboot/activity recreate и обе темы/повороты. Сделай реальные рендеры Compose: Elegant и Classic в portrait, landscape и CW/CCW; визуально сравни и устрани грубые ошибки.

Если Android/AVD не работает, используй доступные средства тестирования, но прямо обозначь отсутствие прогона на ТВ. Если файловый picker отсутствует — реализуй адекватную альтернативу или подробно зафиксируй аппаратный blocker.

## Самостоятельность и границы полномочий

- Разрешено самому планировать этапы, писать/переделывать код, тесты, документацию, создавать коммиты и ветку, открывать и обновлять **Draft PR** — без постоянных вопросов о каждом изменении.
- **Не разрешено:** сливать в `main`, публиковать релиз для мечети, включать Device Owner/kiosk на живом ТВ, ставить APK на чужое устройство и подменять неопределённые официальные данные без отдельного Owner GO.
- По возможности один рабочий feature branch и один понятный Draft PR с логически разделёнными коммитами. Если слишком большой объём — допускаются связанные PR, но не останавливай работу сразу после первого, если можешь продолжить в своей ветке.
- Сам выбери простые технические решения; не строй платформу ради будущих гипотетических мечетей. Не запрашивай уточнений, когда можно принять безопасное обратимое инженерное решение.
- Если блокирует только **неизвестная модель ТВ или неподтверждённое расписание**, не прекращай работу над остальными функциями. Оставь конкретную проверку на аппаратуре/утверждение данных как документированный blocker, не придумывая результаты.

## Формат конечного отчёта

Максимум 6 коротких пунктов: **что сделано; что работает; сборки/тесты/CI; что не проверено на ТВ; критичные риски; ссылка на Draft PR + скриншоты**. Если цель частично недостижима — назвать точные невыполненные критерии и причину. Не выдавать этапы за выполненные только на основании зелёного CI.
